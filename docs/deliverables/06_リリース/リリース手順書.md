# 勤怠管理システム リリース手順書

## 1. 前提

- リリース責任者と作業者を分け、作業日時と停止時間を社内周知する。
- 対象Gitコミット、リリースノート、DB変更、ロールバック条件を確定する。
- VPN、TLS、MFA、DNS、バックアップ先を準備する。
- `.env`はサーバーだけへ保存し、アクセス権を運用管理者へ限定する。

## 2. リリース判定

次をすべて満たした場合だけ本番リリースする。

- Backendテスト、Frontend build・lint、依存関係監査が成功
- Dockerイメージのビルドとヘルスチェックが成功
- 高優先度の受入テストがすべてOK
- 重大・高の未解決不具合が0件
- DBバックアップと復元試験が成功
- セキュリティ担当がVPN、TLS、MFA、秘密情報設定を確認

## 3. 初回リリース

1. GitHubの対象コミットを社内サーバーへ取得する。
2. `.env.example`を参考に、Git管理外の安全な場所へ本番環境変数を設定する。
3. 32文字以上のDBパスワードと16文字以上の初期管理者パスワードを生成する。
4. `APP_DEMO_SEED_ENABLED=false`、`APP_TEST_USER_ENABLED=false`、`SESSION_COOKIE_SECURE=true`を確認する。
5. TLS終端のリバースプロキシからFrontendへ接続し、HTTPをHTTPSへ転送する。
6. 次を実行する。

```powershell
docker compose pull
docker compose build --pull
docker compose up -d
docker compose ps
```

7. DBとBackendがhealthy、Frontendがrunningであることを確認する。
8. 管理者でログインし、初期パスワードを変更する。
9. 利用者、会社休日、必要な過去Excel勤務表を登録する。
10. ログイン、勤務表作成・保存・履歴、Excel出力、管理者代理参照をスモークテストする。

## 4. 更新リリース

1. `git fetch`後、対象コミットと差分を確認する。
2. `pg_dump -Fc`で直前バックアップを取得し、ファイルを検証する。
3. `docker compose build --pull`で新しいイメージを作成する。
4. 停止時間を開始し、`docker compose up -d`で更新する。
5. Flyway履歴とBackendログを確認する。
6. スモークテストを実行する。
7. 問題がなければ利用再開を周知し、リリースノートへ実施日時とコミットを追記する。

## 5. ロールバック

- アプリだけの問題でDB互換性がある場合、直前コミットのイメージへ戻す。
- DB変更を伴い後方互換性がない場合、利用を停止し、責任者承認後に直前バックアップから復元する。
- 適用済みFlyway SQLを手作業で削除・編集しない。
- ロールバック後も原因調査用ログと失敗時刻を保全する。

## 6. リリース後確認

- 翌営業日にログイン失敗、APIエラー、DB容量、バックアップ結果を確認する。
- 1週間は問い合わせと性能を重点監視する。
- 発生した不具合はテスト仕様書の不具合記録とリリースノートへ紐付ける。
